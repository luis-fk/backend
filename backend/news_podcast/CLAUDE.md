# news_podcast context

The daily news episode, sent to Telegram as one voice message. Text through LangChain (`TextModels` in `api/core/llm.py`, with langchain-google-genai and langchain-openai), the voice behind `api/core/voice/` (`narrate` over a `VoiceProvider`; `GeminiVoice`, Gemini's Interactions API over raw httpx, is the only implementation), feedparser, trafilatura, googlenewsdecoder, ffmpeg, Telegram Bot API. It runs as `python manage.py news_podcast [episode|chat-id]`, daily on a Railway cron service (`episode --scheduled`, cron `40 9 * * *`, sent around 07:00 BRT; setup in `news_podcast/README.md`). Its settings and run history live in `news_podcast_db` and are edited in the Django admin. This file holds the app's decisions; `backend/CLAUDE.md` has the rules every app follows. Paths are relative to `backend/`.

## Decisions
- **Layers:** `api/core/` holds what the episode and the later lesson share (config, schemas, turns, messages, costs, audio, Telegram, the attempt rules both models use in `retries.py`, the text models in `llm.py`, the voice in `voice/`) and never uses the ORM; `api/episode/` is the daily episode (its config, schemas, feeds, articles, options, prompts, selection, script, messages, the service and `run.py`). The ORM runs only in `models.py`, `admin.py`, the commands and the features' `run.py`, outside the event loop: `run.py` reads `PodcastSettings` and the feeds and hands `EpisodeService` a frozen `EpisodeSettings` snapshot. Core never imports a feature or the models, the features never import each other, and they reach the voice only through `voice/base.py`, `voice/providers.py` and `voice/narration.py`, so an implementation stays behind `voice_provider` (`tests/news_podcast/test_import_rules.py` checks it, relative imports included). The command only parses its arguments, sets up logging and calls `run.py` (or, for `chat-id`, `report_chat_ids` in `api/core/telegram.py`).
- **Schedule:** runs only on Railway (by hand: Run now or `railway cron run`); do not move runs back to GitHub, which delayed or dropped scheduled runs and can't reach the database. The episode goes out as soon as it is ready, with no wait in the process: a process waiting for the hour could die with a paid-for episode, and with no notice or history, which come after the send. It is named after the next full hour after the start (`next_send`) and its news ends at the full hour before, so the Railway cron alone sets the time and frequency, starting about 20 minutes before that hour: no schedule in a UI or a variable. A run stops after `MAX_RUN_MINUTES` (2 hours) and warns the admin chat, because Railway doesn't start a scheduled run while one is running, so a stuck run would block the next days. A backend deploy also redeploys the cron service and stops a running execution with no grace, so releases to `main` stay out of the run (06:40 BRT until the episode is out). The limit acts at an await, so a thread that never returns (trafilatura runs in one) would still hold the process; accepted, since every network call has its own timeout.
- **Settings:** length, speed, the models with their prices, the prompts and the voice styles are one `PodcastSettings` row; `clean()` refuses bad values on save, so they never reach a run. Text model names are `provider:model` with LangChain's names (`google_genai`, `openai`); a bare `gemini-*` name means `google_genai`, so the saved settings keep working, and `clean()` refuses any other provider. The voice model follows the same names, with its providers in `VOICE_PROVIDERS` (`api/core/voice/providers.py`), which `voice_provider` builds from and `clean()` checks: only `google_genai` today. `Usage.model` and the keys of `prices()` keep the name as saved, so a cost never drops to 0 because a name changed form. The row, the feed list and the lesson catalog come only from `seed/` (JSON, read only by `seed_news_podcast`: `make seed`, `make seed-prod`), which creates the settings row when there is none and fills the feed list and the catalog when they are empty, and never changes a row; the code holds no starting value, and no field but `paused` has a default. Without the row, `load()` raises `SettingsMissing`, which the run reports at 'configurações' and the admin's Settings page shows. Migrations are for schema changes only (the owner's rule). The admin's permissions must not query this database (the admin checks them on every page). `paused` stops the `--scheduled` runs. Prices are edited by hand (they double on 2027-01-01).
- **History:** every run that gets its settings saves an `Episode` row (its kind, news or lesson, status, length, the script's words, paid-plan cost in USD, tokens, failed step and error), never the audio; a failed run keeps the cost of the answers it got, broken ones included. The admin shows costs in BRL with the fixed `BRL_PER_USD` (no exchange-rate API). `api/episode/run.py` uses the ORM only outside the event loop and renews the connection before writing the history, since a run can last up to 2 hours.
- **Catalog:** the lessons' areas and topics live in the admin, in teaching order by position (ties broken by id, the area's id first, so an area's topics stay together). A topic is taught when a `sent` lesson row points to it (`Topic.objects.with_taught_at()`); deleting that row in the history frees it. `Episode.topic` is `PROTECT`, so a taught topic, and its area, can't be deleted: untick it. The lesson fields of `Episode` (`kind`, `story_title`, `pages`) have a `db_default`, so the code on either side of a release can insert rows while the migration and the deploy happen in either order.
- **Length and speed:** length is the delivered file's duration, so a faster speed means a longer script and more voice cost; `max minutes × speed` is capped at `MAX_SPEECH_MINUTES` (30) to fit the free tier's 10 voice requests a day. The seed starts the speed at 1.0, since listeners use Telegram's speed button.
- **Episode:** a single Telegram voice message (OGG/Opus via `sendVoice`) with a one-line caption, because only voice messages get the speed button. It opens with a TV-news "escalada" (3–5 short headlines, read with the emphatic headline style), without copying any real show. The voice is behind `core/voice`, with `GeminiVoice` as the only implementation: the service builds it with `voice_provider` inside the 'voz' step, so a voice model with no implementation or a missing `GEMINI_API_KEY` fails that step with its notice and history row, and `narrate` reads the chunks with each host's voice for the provider (`HOSTS`). The voice model and styles were chosen by ear; the TTS has no speaking-rate parameter, so pace comes from the style, and `NATURAL_WORDS_PER_MINUTE` (170) must be recalibrated when the voice or the style changes. The history's words per minute (at speed 1.0) show the real pace.
- **Feeds:** `Feed` rows edited in the admin, which `api/episode/run.py` reads outside the event loop. The list comes from the seed and an empty one is never refilled, so a run then fails at 'leitura dos feeds'; it is read in section order, since the first feed's copy of a repeated headline stays. Only open-access sites whose domain is in `FULL_TEXT_DOMAINS` (no paywalls, no sites that block automated reading); never bypass bot protection. A video page (a `video` or `videos` segment in its path, like SBT's) has no text, so it is never read and another outlet takes its slot; that's why every candidate's Google News link is decoded before the picking. A Google News search returns at most 100 items, so big sites (CNN Brasil, Poder360) come in by section, and the SBT search leaves its video pages out (`-site:sbtnews.sbt.com.br/videos`); an outlet's feeds share its name, so the dedup and the one-source-per-outlet rule still hold. CNN Brasil comes in for politics only: its economy and international sections added about 120 headlines a day, mostly stories no other outlet ran, plus index pages and old articles dated today, so they were dropped (the owner's choice, 2026-11-09).
- **Selection:** the model ranks the facts by the prompt's priorities and by how many different outlets reported each one, counting each outlet once, so an outlet that publishes many headlines doesn't weigh more. The headlines reach it in time order.
- **Chats:** `TELEGRAM_CHAT_ID` is a single chat (a group, to reach more people). Error notices (a refused send included) and the `chat-id` list go to `TELEGRAM_ADMIN_CHAT_ID`, falling back to `TELEGRAM_CHAT_ID`.
- **Text answers:** every text request goes through `TextModels.ask` (`api/core/llm.py`), with structured output: the step's Pydantic serialization schema, where every field is required, goes to `with_structured_output(method="json_schema", include_raw=True)`, and the raw text is read with a strict `json.loads` and validated with the model: LangChain's parser closes what a cut answer left open, which would let a truncated script through. The field descriptions (in Portuguese) explain the format, and the prompts never ask for JSON. Only Gemini is held to the schema: ChatOpenAI binds a dict schema with strict off, so an OpenAI answer is validated like any other and asked again when it breaks. The saved prompt is the system message (`ChatPromptTemplate`) and the step's material a variable of the human message, so its braces are never read as placeholders. Each answer's usage comes from `usage_metadata` and counts before the answer is checked; the log shows the finish reason of an answer that stopped early and where its JSON breaks.
- **Fallbacks:** `TextModels` is one per `asyncio.run`, so its waits and model marks belong to the run. Text falls back to the fallback model after a second try on the same one (`ANSWERS_PER_MODEL`). The providers' own retries are off (`max_retries` 1 for `google_genai`, where it counts attempts, and 0 for `openai`) and ours stay: up to 3 attempts for a 500, 502, 503 or 504, a per-minute 429 or a connection error, waiting Gemini's `retryDelay` or OpenAI's `Retry-After`, or else `RATE_LIMIT_WAIT_SECONDS` times the attempt after a 429 and a backoff otherwise; a timeout (a 408 included) ends the model's turn at once. An error the sorting doesn't know counts as a failed answer, as before, so the next model still gets its turn. A model that is down is skipped until the next wait. One out of quota (Gemini's `PerDay` quota, OpenAI's `insufficient_quota`) or refused (its key missing from the Django settings, an unknown provider, another 4xx) is skipped for the rest of the run, with the provider's message in the log and the error. google-genai sends Gemini's requests through aiohttp, a declared dependency for that reason, so its timeouts and connection errors arrive as asyncio's and aiohttp's classes. When no text model answers well while one of them is marked down (in this step or an earlier one), the run waits `TEXT_RETRY_MINUTES` and asks them all again; the waits are shared by the whole run. With no model down, bad answers and a used-up quota fail at once, and the request to lengthen the script never waits (`wait=False`: the short one will do). Voice has no fallback (the user prefers no episode over another voice): it retries after `VOICE_RETRY_MINUTES` and then fails with a Telegram message.
- **Kept out on purpose:** voice and plan variables, the Microsoft voice and the `samples` action; do not add them back unless asked.
