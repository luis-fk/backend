# news_podcast context

The daily news episode, sent to Telegram as one voice message. Gemini API over raw httpx (text with `generateContent`, TTS with the Interactions API), feedparser, trafilatura, googlenewsdecoder, ffmpeg, Telegram Bot API. It runs as `python manage.py news_podcast [episode|chat-id]`, daily on a Railway cron service (`episode --scheduled`, cron `40 9 * * *`, sent around 07:00 BRT; setup in `news_podcast/README.md`). Its settings and run history live in `news_podcast_db` and are edited in the Django admin. This file holds the app's decisions; `backend/CLAUDE.md` has the rules every app follows. Paths are relative to `backend/`.

## Decisions
- **Layers:** `api/core/` holds what the episode and the later lesson share (config, schemas, turns, messages, costs, audio, Telegram, the Gemini client) and never uses the ORM; `api/episode/` is the daily episode (its config with the starting values, schemas, feeds, articles, options, prompts, selection, script, messages, the service and `run.py`). The ORM runs only in `models.py`, `admin.py`, the commands and the features' `run.py`, outside the event loop: `run.py` reads `PodcastSettings` and the feeds and hands `EpisodeService` a frozen `EpisodeSettings` snapshot. Core never imports a feature or the models, and the features never import each other (`tests/news_podcast/test_import_rules.py` checks it, relative imports included). The command only parses its arguments, sets up logging and calls `run.py`.
- **Schedule:** runs only on Railway (by hand: Run now or `railway cron run`); do not move runs back to GitHub, which delayed or dropped scheduled runs and can't reach the database. The episode goes out as soon as it is ready, with no wait in the process: a process waiting for the hour could die with a paid-for episode, and with no notice or history, which come after the send. It is named after the next full hour after the start (`next_send`) and its news ends at the full hour before, so the Railway cron alone sets the time and frequency, starting about 20 minutes before that hour: no schedule in a UI or a variable. A run stops after `MAX_RUN_MINUTES` (2 hours) and warns the admin chat, because Railway doesn't start a scheduled run while one is running, so a stuck run would block the next days. A backend deploy also redeploys the cron service and stops a running execution with no grace, so releases to `main` stay out of the run (06:40 BRT until the episode is out). The limit acts at an await, so a thread that never returns (trafilatura runs in one) would still hold the process; accepted, since every network call has its own timeout.
- **Settings:** length, speed, the Gemini models (free text) with their prices, the prompts and the voice styles are one `PodcastSettings` row; `clean()` refuses bad values on save, so they never reach a run. `api/episode/config.py` and `api/episode/prompts.py` only hold the starting values. The fields read them through `starting_value` (`STARTING_VALUES` in `models.py`), so a migration records only the field's name and editing a starting value needs none: migrations are for schema changes only (the owner's rule). The admin's permissions must not query this database (the admin checks them on every page). `paused` stops the `--scheduled` runs. Prices are edited by hand (they double on 2027-01-01).
- **History:** every run saves an `Episode` row (status, length, the script's words, paid-plan cost in USD, tokens, failed step and error), never the audio; a failed run keeps the cost of the answers it got, broken ones included. The admin shows costs in BRL with the fixed `BRL_PER_USD` (no exchange-rate API). `api/episode/run.py` uses the ORM only outside the event loop and renews the connection before writing the history, since a run can last up to 2 hours.
- **Length and speed:** length is the delivered file's duration, so a faster speed means a longer script and more voice cost; `max minutes × speed` is capped at `MAX_SPEECH_MINUTES` (30) to fit the free tier's 10 voice requests a day. Speed defaults to 1.0, since listeners use Telegram's speed button.
- **Episode:** a single Telegram voice message (OGG/Opus via `sendVoice`) with a one-line caption, because only voice messages get the speed button. It opens with a TV-news "escalada" (3–5 short headlines, read with the emphatic headline style), without copying any real show. The voice model and styles were chosen by ear; the TTS has no speaking-rate parameter, so pace comes from the style, and `NATURAL_WORDS_PER_MINUTE` (170) must be recalibrated when the voice or the style changes. The history's words per minute (at speed 1.0) show the real pace.
- **Feeds:** `Feed` rows edited in the admin, which `api/episode/run.py` reads outside the event loop. The list starts with `STARTING_FEEDS` (`api/episode/config.py`) when the table is empty, and it is read in section order, since the first feed's copy of a repeated headline stays. Only open-access sites whose domain is in `FULL_TEXT_DOMAINS` (no paywalls, no sites that block automated reading); never bypass bot protection. A video page (a `video` or `videos` segment in its path, like SBT's) has no text, so it is never read and another outlet takes its slot; that's why every candidate's Google News link is decoded before the picking. A Google News search returns at most 100 items, so big sites (CNN Brasil, Poder360) come in by section, and the SBT search leaves its video pages out (`-site:sbtnews.sbt.com.br/videos`); an outlet's feeds share its name, so the dedup and the one-source-per-outlet rule still hold. CNN Brasil comes in for politics only: its economy and international sections added about 120 headlines a day, mostly stories no other outlet ran, plus index pages and old articles dated today, so they were dropped (the owner's choice, 2026-11-09).
- **Selection:** the model ranks the facts by the prompt's priorities and by how many different outlets reported each one, counting each outlet once, so an outlet that publishes many headlines doesn't weigh more. The headlines reach it in time order.
- **Chats:** `TELEGRAM_CHAT_ID` is a single chat (a group, to reach more people). Error notices (a refused send included) and the `chat-id` list go to `TELEGRAM_ADMIN_CHAT_ID`, falling back to `TELEGRAM_CHAT_ID`.
- **Text answers:** structured output. Each step sends its Pydantic model's serialization schema (`responseJsonSchema`), where every field is required and the field descriptions in the schemas (in Portuguese) explain the format, so Gemini can only write JSON that follows it and the prompts never ask for JSON. An answer cut short can still break: the log shows the finish reason of an answer that stopped early and where its JSON breaks.
- **Fallbacks:** text falls back to the fallback model after a second try on the same one (`ANSWERS_PER_MODEL`). A model that is down (5xx, timeouts) is skipped until the next wait, and one out of quota for the rest of the run. When no text model answers well while one of them is marked down (in this step or an earlier one), the run waits `TEXT_RETRY_MINUTES` and asks them all again; the waits are shared by the whole run. With no model down, bad answers and a used-up quota fail at once, and the request to lengthen the script never waits (the short one will do). Voice has no fallback (the user prefers no episode over another voice): it retries after `VOICE_RETRY_MINUTES` and then fails with a Telegram message.
- **Kept out on purpose:** voice and plan variables, the Microsoft voice and the `samples` action; do not add them back unless asked.
