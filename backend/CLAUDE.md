# Backend context

## What this part does
The Django backend of the monorepo; the root `CLAUDE.md` has the repository layout, the rules shared with the frontend and the BMAD notes. Paths below are relative to `backend/`.
It hosts four independent apps: **plants** (plant data ingestion and an AI chatbot), **political_culture** (political text analysis and word counting with semantic search), **cfflch** (college admission status checker via web search and PDF parsing), and **news_podcast** (daily news audio briefing sent to Telegram).
The Next.js frontend that serves their UIs lives in `../frontend`. `README.md` covers setup and commands.

## Tech stack
- **Runtime:** Python 3.12+. `runtime.txt` asks Railway for the latest 3.12: Railpack installs Python with mise, which had no build of an exact old patch like 3.12.1
- **Frameworks:** Django 6, Django REST Framework, Django Channels (WebSockets)
- **ASGI server:** Daphne
- **Databases:** PostgreSQL — one database per app (`default` for auth and the API keys, `plants_db`, `political_culture_db`, `cfflch_db`, `news_podcast_db`). Redis for the Django Channels layer outside development; with `ENVIRONMENT=development` the layer is in memory.
- **ORM:** Django ORM, routed via a custom `AppsRouter` in `backend/apps_routers.py`
- **Auth:** Users log in to the frontend by name, and the frontend keeps the session. The API checks HS256 JWTs the frontend signs with `API_TOKEN_SECRET` (PyJWT, `backend/api_auth.py`); Bruno and anyone the owner gives access use API keys created in the Django admin (the `api_keys` app stores only their SHA-256 hash); a key acts as one person in one or more apps, keeping the person's id in each app's Users table (`ApiKey.users`), and the person and the apps are set once, when the key is created; each ESP32 sends its own device key as `X-Device-Key` (`Esp32Device`, created in the admin, which stores only its SHA-256 hash), checked in plants (`device_for_key`), and the key stops when the device is unticked or its owner is blocked. Only the owner can create accounts (Django admin). No public registration. Unticking a person's Active, or one of their apps, blocks them at once and keeps their data: the login, and every user token and API key (`can_use` in `api_keys/app_users.py`), need both the auth user and the person's row in the app's Users to be active.
- **AI/ML:** LangChain, LangGraph, OpenAI (`gpt-4.1-mini`, `gpt-4o-mini`), Tavily (web search), pgvector (semantic search — used in `political_culture`)
- **External APIs:** OpenWeather (used in `plants` for weather data)
- **news_podcast:** Gemini API over raw httpx (text with `generateContent`, TTS with the Interactions API), feedparser, trafilatura, googlenewsdecoder, ffmpeg, Telegram Bot API
- **HTTP client:** httpx (async)
- **Linting/formatting:** Ruff (both lint and format)

## Architecture
- Django monolith; the Next.js frontend in `../frontend` serves the UIs and talks to it only over HTTP and WebSocket
- Each app follows the structure: `<app>/api/<feature>/routes.py`, `service.py`, `serializers.py`, and additional files as needed (e.g. `consumers.py` for WebSockets, `utils.py`, `prompts.py`)
- **Parnas decomposition is intentional:** each app owns its full logic stack. Do not extract shared utilities across apps even if code looks duplicated — duplication is preferred over coupling. The exceptions, approved by the owner, are two pieces of project infrastructure, like `settings.py` and `asgi.py`: `backend/api_auth.py`, with the token and API key checks every app uses, and the `api_keys` app, with the `ApiKey` model and its admin, and the admin's user pages. The apps never import `api_keys`; it finds their Users models by name (`app_users.py`).
- **People and apps:** a person is an auth user, and each app's `Users` row points to them by `auth_user_id`, since every app has its own database; login looks the name up in auth, then in the app. The admin's user form sets the apps a person can use: unticking one turns off `active` on their row there, which blocks them and keeps their data (deleting the row would delete the data, so that is left to the app's Users table, which lists what goes with it). Active sits next to the apps on the user page and in the user list, which also shows each person's apps; each app's Users table shows and searches the name and filters by `active`.
- The `AppsRouter` automatically routes models to their app-specific database; Django's own apps and `api_keys` go to `default` (`DEFAULT_DB_APPS`). Never use `using=` manually in queries — the router handles it.
- **Local data and commands:** `make seed` runs one command per app (`seed_plants`, `seed_political_culture`, `seed_cfflch`) for the person `demo`; a second run replaces only what the seed made. The seeds, `make migrate` (which `make superuser` runs first) and the tests refuse databases outside this machine, since `backend/.env` may hold the production URLs: the project's code (`migrate_all`, the tests) uses `backend/local_databases.py`, and each seed has its own copy of the check, because the apps share no code. The project package `backend` is an installed app only for its commands. The political culture seed reads `political_culture/seed/`: the text, the words of its word count, and the text's vector, made once with OpenAI's `text-embedding-ada-002` (the model of the chat's search), so a change to the text needs a new vector.
- Separation of concerns: routes handle HTTP only, services contain business logic, serializers handle validation. Keep functions small.
- **API documentation:** the Bruno collection in `bruno/`, with no Swagger. A new or changed endpoint updates its request there. Values that belong to one person (API keys, user ids, tokens) are secret variables of the Local environment, and bodies use made-up names, so the committed files stay generic.

## Coding conventions
- **Files and functions:** `snake_case`
- **Classes:** `PascalCase`
- **DB columns:** `snake_case`
- **API endpoints:** `kebab-case` (dashes, e.g. `/admission-status/`)
- **Linter/formatter:** Ruff — always run before committing
- **Type hints:** mandatory everywhere except trivially obvious assignments (e.g. `name = "Felipe"` needs no annotation). Return types are always annotated.
- **Comments:** not used — code should be self-explanatory through naming. Only add a comment when the *why* is non-obvious (a hidden constraint, a workaround, a subtle invariant).
- **Error handling:** return structured JSON errors with appropriate HTTP status codes. Prefer fine-grained error responses over generic 500s. Log errors at service level with `logging`, don't swallow them silently.
- **Async:** used throughout for IO-bound work. Background tasks use `asyncio.ensure_future` with a `done_callback` for error logging. `asyncio.gather` for concurrent fan-out.

## Current state
**Complete (stable):**
- `political_culture`: a shared texts library (`api/texts/`), the word counter with LLM extraction, and a political chatbot with tools. pgvector is used to semantically search long reference texts that would otherwise exceed context limits. Library decisions:
  - Any user lists the library and adds PDFs of up to 100 MB. Only the Django admin edits or deletes a text, since a delete would remove it for everyone.
  - A PDF already in the library, by its SHA-256 (`Texts.file_hash`), or still being read (a set in memory, enough for the single process) is refused with 409, so it isn't read and paid for twice.
  - A book takes minutes, so `POST /api/political-culture/texts` answers 202 and a thread reads the PDF: embeddings, then title, author and summary, then word count, saved in one transaction. The result goes to the uploader's socket `ws/political-culture/texts/<userId>`, which isn't re-delivered, with the `upload_id` the page picked and sent: a PDF that fails at once may answer on the socket before the 202 arrives. A restart mid-reading loses the upload, and the user sends it again.
  - Text from PyPDF loses its NUL characters and lone surrogate halves, and the model's title and author are cut to their columns: PostgreSQL refuses them, and the whole reading would fail after being paid for.
  - The word picker gets only the 200 most frequent words (`MAX_PICKER_WORDS`): the analyses compare each text's key terms, and in a book about two thirds of the top 100 are function words, which the model drops.
  - Each user ticks the library texts the AI uses in their analyses (`Texts.selected_by`, set with `PUT /api/political-culture/texts/<id>/selection`). Every text, old or new, starts unticked. The tools that read the library are built per user (`user_tools` in `chatbot/tools.py`), so they see only that user's ticked texts and the texts they pasted in the chat.
  - The chat answers `/help` (any case) with a fixed text in `help.py`, in the page's language (`language` in the message: `pt-BR`, the default, or `en`), without the model. The command and the answer stay in the history, which the chat reads, so the bot knows what it showed. An empty chat opens with the same text and a line about `/help`, from `GET /api/political-culture/chatbot/help?language=…`; that first message isn't saved. Any other message is answered in the language it is written in (the prompts say so).
  - The text search (`query_vectors`) returns the 3 best chunks, and the model can ask for the text around one of them (`get_surrounding_text`): at most 2 chunks before and after, in reading order (chunk ids, within the text). It answers only for chunks the search returned in the same answer, so the model can't walk through a text by guessing ids. Where two chunks meet, the overlap they repeat comes once when it has 20 characters or more, so a short heading at a seam can still repeat.
- `cfflch`: admission status checker — searches Tavily for PDFs, downloads and parses them, streams results over WebSocket. Has its own dedicated database (`cfflch_db`).
- `plants`: ESP32 data ingestion, OpenWeather integration for weather data, AI chatbot. After the tools run, the `tool_response` node answers from their results and may ask for more (see below). It is a plant-care assistant in a plain, friendly voice (it used to speak as a pirate) and answers in the language of the person's latest message. Each ESP32 is an `Esp32Device` with its plant's nickname (unique per person), its owner and its soil calibration (`dry_value` reads 0%, `wet_value` 100%; swapping them inverts the scale). Readings keep their device; the site reads them through `GET /api/plants/devices/` and `GET /api/plants/devices/<id>/readings/?hours=24|168|720`, with the soil as a percentage of the calibration. A reading is saved without the weather when the owner has no location or OpenWeather fails, since the soil reading is the plant's own data. Readings from before the devices have none and don't show. The chat has two tools for the person's plants, `list_my_plants` and `get_plant_readings` (`plants/api/chatbot/tools.py`, built on `plants/api/sensors/summary.py`): they get the person through LangGraph's `InjectedState`, so the model never names them, find a plant by its nickname as typed or, when only one matches, ignoring case, and give times in São Paulo's zone. The model may answer from tool results up to 4 times per answer (`MAX_TOOL_ROUNDS`), the last time without tools, and `more_tools` stops at the limit too. A failing tool comes back to the model as an error (`handle_tool_errors`). The prompts give the current time in São Paulo, like the tools, and the router sees the exchange before the latest message. The ToolNode runs tools in worker threads, so the plant tools close their database connections, and the tests that run them through the graph commit their rows (`transaction=True`).

- `news_podcast`: runs as `python manage.py news_podcast [episode|chat-id]`, daily on a Railway cron service (`episode --scheduled`, cron `40 9 * * *`, sent around 07:00 BRT; setup in `news_podcast/README.md`). Its settings and run history live in `news_podcast_db` and are edited in the Django admin. Decisions:
  - **Schedule:** runs only on Railway (by hand: Run now or `railway cron run`); do not move runs back to GitHub, which delayed or dropped scheduled runs and can't reach the database. The episode goes out as soon as it is ready, with no wait in the process: a process waiting for the hour could die with a paid-for episode, and with no notice or history, which come after the send. It is named after the next full hour after the start (`next_send`) and its news ends at the full hour before, so the Railway cron alone sets the time and frequency, starting about 20 minutes before that hour: no schedule in a UI or a variable. A run stops after `MAX_RUN_MINUTES` (2 hours) and warns the admin chat, because Railway doesn't start a scheduled run while one is running, so a stuck run would block the next days. A backend deploy also redeploys the cron service and stops a running execution with no grace, so releases to `main` stay out of the run (06:40 BRT until the episode is out). The limit acts at an await, so a thread that never returns (trafilatura runs in one) would still hold the process; accepted, since every network call has its own timeout.
  - **Settings:** length, speed, the Gemini models (free text) with their prices, the prompts and the voice styles are one `PodcastSettings` row; `clean()` refuses bad values on save, so they never reach a run. `config.py` and `prompts.py` only hold the starting values. The fields read them through `starting_value` (`STARTING_VALUES` in `models.py`), so a migration records only the field's name and editing a starting value needs none: migrations are for schema changes only (the owner's rule). The admin's permissions must not query this database (the admin checks them on every page). `paused` stops the `--scheduled` runs. Prices are edited by hand (they double on 2027-01-01).
  - **History:** every run saves an `Episode` row (status, length, the script's words, paid-plan cost in USD, tokens, failed step and error), never the audio; a failed run keeps the cost of the answers it got, broken ones included. The admin shows costs in BRL with the fixed `BRL_PER_USD` (no exchange-rate API). The command uses the ORM only outside the event loop and renews the connection before writing the history, since a run can last up to 2 hours.
  - **Length and speed:** length is the delivered file's duration, so a faster speed means a longer script and more voice cost; `max minutes × speed` is capped at `MAX_SPEECH_MINUTES` (30) to fit the free tier's 10 voice requests a day. Speed defaults to 1.0, since listeners use Telegram's speed button.
  - **Episode:** a single Telegram voice message (OGG/Opus via `sendVoice`) with a one-line caption, because only voice messages get the speed button. It opens with a TV-news "escalada" (3–5 short headlines, read with the emphatic headline style), without copying any real show. The voice model and styles were chosen by ear; the TTS has no speaking-rate parameter, so pace comes from the style, and `NATURAL_WORDS_PER_MINUTE` (170) must be recalibrated when the voice or the style changes. The history's words per minute (at speed 1.0) show the real pace.
  - **Feeds:** `Feed` rows edited in the admin, which the command reads outside the event loop. The list starts with `STARTING_FEEDS` (`config.py`) when the table is empty, and it is read in section order, since the first feed's copy of a repeated headline stays. Only open-access sites whose domain is in `FULL_TEXT_DOMAINS` (no paywalls, no sites that block automated reading); never bypass bot protection. A video page (a `video` or `videos` segment in its path, like SBT's) has no text, so it is never read and another outlet takes its slot; that's why every candidate's Google News link is decoded before the picking. A Google News search returns at most 100 items, so big sites (CNN Brasil, Poder360) come in by section, and the SBT search leaves its video pages out (`-site:sbtnews.sbt.com.br/videos`); an outlet's feeds share its name, so the dedup and the one-source-per-outlet rule still hold. CNN Brasil comes in for politics only: its economy and international sections added about 120 headlines a day, mostly stories no other outlet ran, plus index pages and old articles dated today, so they were dropped (the owner's choice, 2026-11-09).
  - **Selection:** the model ranks the facts by the prompt's priorities and by how many different outlets reported each one, counting each outlet once, so an outlet that publishes many headlines doesn't weigh more. The headlines reach it in time order.
  - **Chats:** `TELEGRAM_CHAT_ID` is a single chat (a group, to reach more people). Error notices (a refused send included) and the `chat-id` list go to `TELEGRAM_ADMIN_CHAT_ID`, falling back to `TELEGRAM_CHAT_ID`.
  - **Text answers:** structured output. Each step sends its Pydantic model's serialization schema (`responseJsonSchema`), where every field is required and the field descriptions in `schemas.py` (in Portuguese) explain the format, so Gemini can only write JSON that follows it and the prompts never ask for JSON. An answer cut short can still break: the log shows the finish reason of an answer that stopped early and where its JSON breaks.
  - **Fallbacks:** text falls back to the fallback model after a second try on the same one (`ANSWERS_PER_MODEL`). A model that is down (5xx, timeouts) is skipped until the next wait, and one out of quota for the rest of the run. When no text model answers well while one of them is marked down (in this step or an earlier one), the run waits `TEXT_RETRY_MINUTES` and asks them all again; the waits are shared by the whole run. With no model down, bad answers and a used-up quota fail at once, and the request to lengthen the script never waits (the short one will do). Voice has no fallback (the user prefers no episode over another voice): it retries after `VOICE_RETRY_MINUTES` and then fails with a Telegram message.
  - **Kept out on purpose:** voice and plan variables, the Microsoft voice and the `samples` action; do not add them back unless asked.

**cfflch behavior (since v2.0.0):**
- `AdmissionPDF` has a `search_title` field (max 512 chars) — populated from Tavily search result title
- `pdf_urls` in the admission results serializer returns `list[dict]` with `url` and `search_title` keys (was `list[str]`); the frontend reads `item.url`
- Admission results endpoint accepts optional `class_room_id` query param filter
- Searched students are saved to DB, found or not (no PDFs = not found). A search that can't run (a Tavily error or no key) or can't read any of the lists it found is sent with `failed: true` and not saved, so searching the name again runs a new search
- Re-searching a known student (same name + year) skips Tavily and returns existing data immediately
- If a known student is re-searched with a different classroom, the classroom is updated
- PDF URL detection uses `.pdf` anywhere in the URL (not just `.endswith`)
- Tavily query includes keywords: `aprovado classificado convocado selecionado vestibular`
- PDF downloads are concurrent via `asyncio.gather`
- Name matching looks for the normalized name as whole words in the normalized text (not fuzzy/per-line matching), so "Ana de Tal" doesn't match "Joana de Tal"

## Testing
- Unit tests run in CI (`uv run pytest` in `.github/workflows/backend-ci.yml` at the repository root) on every pull request that changes `backend/`.
- **Target:** unit tests only, written cleanly and with full understanding — not just for coverage
- **Location:** `tests/` folder (next to `manage.py`) mirroring the app structure
- **Coverage:** all four apps have tests in `tests/<app>/`; the API auth also has `tests/backend/test_api_auth.py` and `tests/api_keys/`
- **Setup:** pytest-django. Tests mock the LLMs and the external APIs and never reach the network. The databases are real in the tests that ask for them with `@pytest.mark.django_db(databases=["default", "<app>_db"])`: always list `default`, or a file run on its own fails with "Circular dependency in TEST[DEPENDENCIES]". Add `transaction=True` only when the code under test closes connections or queries from worker threads. Every token check also reads the person (`can_use`): `tests/conftest.py` lets everyone in, so tests can make up user ids, except in the tests marked `access_check`, which save the person (`saved_person` in `tests/api_tokens.py`). The consumers tidy their thread's connections when a socket opens, so the socket tests ask for the database. pytest-django creates and drops a `test_` copy of each database, on the local PostgreSQL (run `make db-up` first; `tests/conftest.py` stops the run when a database isn't on this machine, where pytest-django would create those copies) or on in-memory SQLite in CI, and the tests must pass on both, so pgvector searches (`CosineDistance`, which SQLite lacks) stay out of the database tests. The settings need `API_TOKEN_SECRET`; CI sets a dummy, plus `OPENAI_API_KEY` because the chatbot views build their clients on import

## Non-negotiables
The shared ones (learning-first, git managed by the user) are in the root `CLAUDE.md`.
- **Keep apps isolated.** Each app is self-contained. Do not suggest cross-app imports or shared utility modules (`backend/api_auth.py` and the `api_keys` app are the only shared code).
- **Every endpoint checks a token.** A new view or consumer starts with a check from `backend/api_auth.py`: `require_user_token` (and `require_same_user` for one user's data) or `require_login_token` in DRF views, `has_valid_user_token` in plain Django views (the ESP32 view checks its device key with plants' `device_for_key`), `websocket_user_id` in consumers (through `database_sync_to_async`, since it reads the database), which accept with `subprotocol="bearer"`. Over HTTP, `require_user_token` and `has_valid_user_token` accept a user token or an API key (`Authorization: Bearer pk_...`); every check reads the database (the person must still be able to use the app), so async views call `has_valid_user_token` through `sync_to_async`. Consumers take user tokens only. Add 401/403 tests in `tests/<app>/`, with keys too.
- **PostgreSQL only.** Do not suggest alternative databases.
- **Multi-DB setup is fixed.** The `AppsRouter` is the source of truth for routing. Adding a new app requires a `<app>_db` entry in `DATABASES`, its URL in `backend/.env.example` and in the CI's environment, its `CREATE DATABASE` in `db/init.sql`, and its `makemigrations` line in the Makefile (`migrate_all` runs every database) — but don't do this until explicitly asked.
- **LangChain APIs change frequently.** Avoid deprecated patterns: `AgentExecutor` is gone, `hub.pull` is not used — prompts live locally in `prompts.py` files. Prefer `llm.bind_tools([...]).invoke(...)`, and run the tool calls it returns and send the results back (`_answer_with_tools` in `political_culture/api/chatbot/agents.py`): a single invoke never runs a tool. When the text is at hand, give it to the model instead of a search tool (the word counter's `extract_text_info`).
- **WebSocket timing in `cfflch`:** the client must connect via WebSocket *before* the POST request is made, otherwise the result message is missed. This is a known limitation — do not try to fix it with polling or re-delivery unless explicitly asked.
- **Railway deployment:** the backend runs on Railway as its own service, with Root Directory `/backend` and watch paths limited to `/backend/**`. The Start Command (set in the Railway dashboard) only starts Daphne; the owner runs the migrations from their machine (`make migrate-prod`: `ENV_FILE` points the settings at `backend/.env.production`, and `migrate_all --production` shows where each database is and asks for `yes`, so `.env` always keeps the local databases). `requirements.txt` is kept in sync (generated with `uv export --no-dev --no-hashes --no-emit-project -o requirements.txt`) so Railway uses pip instead of auto-detecting Poetry.
- **Package manager:** uv only. Do not suggest pip or poetry commands.
