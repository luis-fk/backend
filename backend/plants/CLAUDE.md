# plants context

ESP32 data ingestion, OpenWeather integration for weather data, AI chatbot. This file holds the app's decisions; `backend/CLAUDE.md` has the rules every app follows. Paths are relative to `backend/`.

## Decisions
- **Devices and readings:** Each ESP32 is an `Esp32Device` with its plant's nickname (unique per person), its owner and its soil calibration (`dry_value` reads 0%, `wet_value` 100%; swapping them inverts the scale). Readings keep their device; the site reads them through `GET /api/plants/devices/` and `GET /api/plants/devices/<id>/readings/?hours=24|168|720`, with the soil as a percentage of the calibration. A reading is saved without the weather when the owner has no location or OpenWeather fails, since the soil reading is the plant's own data. Readings from before the devices have none and don't show.
- **Chat:** After the tools run, the `tool_response` node answers from their results and may ask for more (see below). It is a plant-care assistant in a plain, friendly voice (it used to speak as a pirate) and answers in the language of the person's latest message.
- **Chat tools:** The chat has two tools for the person's plants, `list_my_plants` and `get_plant_readings` (`plants/api/chatbot/tools.py`, built on `plants/api/sensors/summary.py`): they get the person through LangGraph's `InjectedState`, so the model never names them, find a plant by its nickname as typed or, when only one matches, ignoring case, and give times in São Paulo's zone. The model may answer from tool results up to 4 times per answer (`MAX_TOOL_ROUNDS`), the last time without tools, and `more_tools` stops at the limit too. A failing tool comes back to the model as an error (`handle_tool_errors`). The prompts give the current time in São Paulo, like the tools, and the router sees the exchange before the latest message. The ToolNode runs tools in worker threads, so the plant tools close their database connections, and the tests that run them through the graph commit their rows (`transaction=True`).
